Three commands, in this order

  1. joomiz validate checks the file against your platform's rules and reports every problem. It changes nothing.
  2. joomiz plan shows what would change. It changes no infrastructure.
  3. joomiz apply makes the change. It refuses a file that was not planned for that environment.

What changes for each team

Developers

  • One file in your repository, next to your code.
  • Check it before you push. Preview every change before you apply it.
  • A VS Code extension gives completion and checks (local install).

Platform teams

  • Define the rules and the building blocks once.
  • Add a building block with a catalog entry (its schema and rules, added to the control plane today) and a provisioner (a service that creates the real resource).
  • Every change goes through the same rules.

Architects

  • The file states the result. The control plane owns the state.
  • Provisioners follow an OpenAPI contract, so you can add your own.
  • Each building block has a closed schema. Mistakes are rejected before anything runs.

Engineering managers

  • Every service declares a golden path: a named choice from the platform's catalog. Today there are two, for Java and Kotlin web applications.
  • Sensitive outputs are recorded in an audit trail.
  • A team can act only on its own applications. Only platform operators can act across teams.
  • Provisioners return secrets as vault references. The control plane rejects a sensitive output that is not a reference.
