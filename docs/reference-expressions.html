A ${{ ... }} expression lets one value in joomiz.yaml point at another, instead of repeating it or hardcoding a value that doesn't exist yet — such as a database password a provisioner hasn't generated until deploy time.

A real example

      deployments:
        - id: billing-service-test-deployment
          type: cloud-foundry-app
          artifact: billing-service-jar
          target: test-foundation
          spec:
            instances: 1
            memory: 512M
            disk-quota: 1G
            buildpack: java_buildpack
            env:
              DB_PASSWORD: "${{managed-resources.billing-service-db.outputs.password}}"

      managed-resources:
        - id: billing-service-vault
          type: azure-key-vault
          spec: { ... }

        - id: billing-service-db
          type: postgres
          spec: { ... }

DB_PASSWORD doesn't hold a password. It holds a reference to one: the password output of the billing-service-db managed resource, in this same environment. When the postgres provisioner creates that database, it writes the real password into billing-service-vault and reports back only a URI naming where it lives. That URI is what this expression resolves to, and it's what the application fetches at startup. The password itself never passes through this file, through the control plane's database, or through a plan output.

The grammar

${{ path }}
path := root ("." segment)+
root := application | targets | deployments | managed-resources | consumed-resources

A path is a root, followed by one or more dot-separated segments. A segment is letters, digits, hyphens, and underscores — the same characters joomiz.yaml's own kebab-case ids use, plus underscores for metadata keys that need them.

A value can hold more than one expression, mixed with literal text:

uri: "${{targets.db.outputs.host}}:5432"

Or it can be exactly one expression and nothing else, as DB_PASSWORD is above.

The seven roots

Root Names
application A field of the application block itself — its own scalars, its owner, or its metadata.
artifacts An entry of the file's top-level artifacts list, named by the path's next segment.
tooling An entry of the file's top-level tooling list, named the same way.
targets An entry of the current environment's targets list.
deployments An entry of the current environment's deployments list.
managed-resources An entry of the current environment's managed-resources list.
consumed-resources An entry of the current environment's consumed-resources list.

Each root is spelled exactly like the key it names in your file, so ${{artifacts.order-service-image.spec.registry}} reads the way the file does.

The first three reach something declared once for the whole file. The last four each reach one entry of one list, and that entry belongs to the same environment the expression is written in.

An artifacts or tooling entry has an id, a type, a spec (and, for a tool, an enabled) — and no outputs. Neither is provisioned per environment and no provisioner reports anything back about one, so ${{artifacts.order-service-image.outputs.digest}} is an error naming what you can read instead.

An expression can't cross environments

There's no environments root. ${{environments.prod.targets.db.spec.host}} isn't a stricter form this grammar happens to reject at read time. It's not a path the grammar can parse at all, because environments isn't one of the seven roots. An expression written in test can only ever name something in test. The grammar enforces this itself, not a check that runs afterward.

This is also why the two environments in the billing-service example can carry the identical expression, ${{managed-resources.billing-service-db.outputs.password}}, once under test and once under prod. Each copy resolves against its own environment's own billing-service-db — the two environments don't share anything by writing the same text.

Naming a resource: spec or outputs

For any of the four resource roots, the path after the resource's id names one of two sections:

  • spec — a field you wrote yourself, under that resource's own spec block.
  • outputs — a field a provisioner reported back after successfully creating that resource. A type's catalog entry defines what fields its outputs can contain, the same way it defines spec. Not every catalog type defines any outputs fields yet. A type with none accepts no outputs reference at all.

managed-resources.billing-service-db.outputs.password in the example above breaks down as: root managed-resources, resource id billing-service-db, section outputs, field password.

To see the outputs a provisioner reported, read the output of joomiz plan or joomiz apply. Below each resource, the CLI prints one line for each field, sorted by field name:

    billing-service-db (created): succeeded — Created 'billing-service-db' (managed-resource/postgres) in environment 'test'.
      outputs.password: https://billing-team-vault.vault.azure.net/secrets/billing-service-db-password

joomiz plan shows the values the provisioner expects to report. joomiz apply shows the values it actually reported, which are the values your expressions resolve to.

A sensitive field, such as password, is meant to hold a reference to a secret store, never the secret itself. The control plane enforces only this much: the value must be an absolute URI with no user name or password in it, and anything else is rejected. It cannot tell a real vault address from another kind of URI. Check what a provisioner reports before you publish the output of joomiz plan or joomiz apply, for example in a CI log that many people can read.

What this syntax does not do

ValueExpressions, the one piece of code that reads this grammar, only answers "what does this text name." It never looks up whether that thing exists, and it never produces a value. Substituting the real value in is a separate step that happens later, when a plan is applied.

Writing a well-formed expression that names a resource your file doesn't declare isn't a syntax error. It's caught elsewhere, as a different kind of problem.

There are no operators, no function calls, no string literals, and no array indexing in this grammar. It names one thing. It doesn't compute one.

Limits

Limit Value
Length of one string value that's scanned for expressions 4096 characters
Expressions in one string value 64
Segments after the root, in one path 16
Length of one segment 255 characters

These limits exist so that checking a file costs a predictable amount of work, no matter what a caller submits. You're unlikely to reach any of them when writing a normal joomiz.yaml by hand.
