The environments block describes where your service runs and what it needs there. It is a top-level key of the file, written at the left margin beside application rather than inside it — see Anatomy of a joomiz.yaml file. This page covers its four lists: targets, deployments, managed-resources, and consumed-resources.

environments is read by joomiz validate, joomiz plan, and joomiz apply. It is not read by joomiz register — see How you use this file.

The shape

environments is a map, not a list. Each key is an environment name, and each value holds the four lists.

environments:
  test:
    targets: [ ... ]
    deployments: [ ... ]
    managed-resources: [ ... ]
    consumed-resources: [ ... ]
  prod:
    targets: [ ... ]
    deployments: [ ... ]
    managed-resources: [ ... ]
    consumed-resources: [ ... ]

An environment name follows the same kebab-case rule as every other id in the file (see Anatomy of a joomiz.yaml file). A file may declare at most 25 environments, and each of the four lists is capped at 50 entries per environment.

Within one environment, every entry across all four lists needs a unique id. That uniqueness doesn't cross environments. test and prod can each declare a managed-resources entry called billing-service-db — they're separate resources in separate environments. The two examples in this guide do exactly that.

targets

A target is where your service runs — a Kubernetes namespace, a Cloud Foundry space, and so on.

    targets:
      - id: test-cluster
        type: kubernetes-namespace
        spec:
          cluster: eu-west-1-test
          namespace: order-service-test

    targets:
      - id: test-foundation
        type: cloud-foundry-space
        spec:
          api-endpoint: https://api.cf.test.internal
          org: joomiz-demo
          space: billing-service-test
Field Required Format Notes
id Yes Kebab-case, unique within this environment A deployments entry's target field names this id.
type Yes Must match a target type the control plane's catalog has registered kubernetes-namespace and cloud-foundry-space, shown above, are two real registered types — not an exhaustive list.
spec Yes A map whose required fields are defined by the catalog entry for type Shape depends on type.

A target references nothing else in the file.

deployments

A deployment says how one artifact runs on one target.

    deployments:
      - id: order-service-test-deployment
        type: kubernetes-deployment
        artifact: order-service-image
        target: test-cluster
        spec:
          replicas: 1
          cpu: 250m
          memory: 512Mi
Field Required Format Notes
id Yes Kebab-case, unique within this environment —
type Yes Must match a deployment type the control plane's catalog has registered —
artifact Yes The id of an entry in the application-level artifacts list See The application block. This is a lookup across the whole file, not just this environment, because artifacts sits outside environments.
target Yes The id of a targets entry in this same environment A deployment can't reference a target declared in a different environment.
spec Yes A map whose required fields are defined by the catalog entry for type Shape depends on type.

Not every artifact or target type is a valid pairing

A deployment type doesn't accept just any artifact type or target type — the control plane's catalog also lists which pairings are permitted. As of this writing, two deployment types are seeded, with these permitted pairings:

Deployment type May reference target type May reference artifact type
kubernetes-deployment kubernetes-namespace container-image
cloud-foundry-app cloud-foundry-space jar

Both example files in this guide follow one of these two pairings exactly. This table, like every catalog type this guide names, is current platform data and can change — see Which tool and resource types can you use?

managed-resources

A managed resource is infrastructure the platform provisions and owns on your application's behalf — a database, a secret store, and so on.

    managed-resources:
      - id: order-service-db
        type: postgres
        spec:
          flavor: db.t3.micro
          version: "16"
          storage-gb: 20
          multi-az: false

    managed-resources:
      - id: billing-service-vault
        type: azure-key-vault
        spec:
          resource-group: billing-service-test-rg
          location: westeurope
          sku: premium
Field Required Format Notes
id Yes Kebab-case, unique within this environment —
type Yes Must match a managed-resource type the control plane's catalog has registered postgres and azure-key-vault, shown above, are two real registered types — not an exhaustive list.
spec Yes A map whose required fields are defined by the catalog entry for type Shape depends on type.

A managed resource references nothing else in the file. What it produces, once provisioned, is available to the rest of its own environment as an outputs reference — see Reference expressions.

consumed-resources

A consumed resource is infrastructure your application depends on but doesn't own or provision — a shared event bus, a shared logging index, and so on.

    consumed-resources:
      - id: shared-event-bus
        type: kafka-topic
        spec:
          topic: orders.test.events

    consumed-resources:
      - id: shared-logging-index
        type: splunk-index
        spec:
          app: billing-observability
          index: billing_test
Field Required Format Notes
id Yes Kebab-case, unique within this environment —
type Yes Must match a consumed-resource type the control plane's catalog has registered kafka-topic and splunk-index, shown above, are two real registered types — not an exhaustive list.
spec Yes A map whose required fields are defined by the catalog entry for type Shape depends on type.

A consumed resource references nothing else in the file, the same as a managed resource.
