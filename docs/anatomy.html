This page shows the overall shape of a joomiz.yaml file, before you look at any one field in detail.

Five top-level keys

A joomiz.yaml file has five top-level keys, and each one answers a different question:

Key What it says
version Which shape of the file this is
application Who your service is: its id, name, repository, Golden Path, and owning team
artifacts What your service is built into — a container image, a jar
tooling What the platform runs for your service — dependency updates, security scans
environments Where your service runs, and what it needs there 
version: 1

application:
  id: 7c1a1e2a-4b3d-4f0a-9c2e-5f6a7b8c9d0e
  name: order-service
  # ... identity fields only

artifacts: [ ... ]
tooling: [ ... ]
environments: { ... }

application holds your service's identity and nothing else. What it builds, what runs for it, and where it runs are keys of their own, written at the left margin beside application rather than indented inside it.

version

Field Required Format Notes
version No The integer 1 Which shape of joomiz.yaml this file is written against. Leave it out and the file is read as version 1, which is what every file written so far means. Write version: 1 and you get exactly the same result.

Today 1 is the only shape that exists, so the field changes nothing about how your file is read. What it does is give a future, structural change to the format something to announce itself with — so that when a second shape arrives, the files you have already written keep working, unedited.

Any other value is rejected: version: 2, version: 0, version: "1" (a string, not a number) and version: 1.5 all come back as an error from joomiz validate, register, plan, and apply alike. The error names the value you sent and the versions this control plane accepts.

joomiz init writes version: 1 into every file it generates.

The two halves of the file

Whatever else it holds, the file has two kinds of content:

  • Declared once for the whole service: the application block (id, name, description, repository, golden-path, owner, metadata), plus artifacts and tooling. See The application block.
  • Declared per environment: the environments map describes where the service runs and what it needs there. Each key is an environment name (test, prod, and so on), and each value is a block of four lists: targets, deployments, managed-resources, and consumed-resources. See The environments block.

Here's the shape with every section named and its content collapsed:

version: 1

application:
  id: ...
  name: ...
  description: ...
  repository: ...
  golden-path: ...
  owner: { ... }
  metadata: { ... }

artifacts: [ ... ]

tooling: [ ... ]

environments:
  test:
    targets: [ ... ]
    deployments: [ ... ]
    managed-resources: [ ... ]
    consumed-resources: [ ... ]
  prod:
    targets: [ ... ]
    deployments: [ ... ]
    managed-resources: [ ... ]
    consumed-resources: [ ... ]

Every YAML key is kebab-case

Keys with more than one word use hyphens, not camelCase or underscores: golden-path, managed-resources, consumed-resources, disk-quota.

One identifier rule, everywhere

Every id you write in this file — the application's name, an environment's name, and the id of every tooling, artifacts, targets, deployments, managed-resources, and consumed-resources entry — follows the same rule:

  • lowercase letters and digits, in groups
  • groups joined by single hyphens
  • no leading, trailing, or doubled hyphens
  • at most 255 characters

order-service, test-cluster, and billing-service-db all follow this rule. Order_Service, -test, and test--cluster don't.

The control plane checks this rule the same way everywhere it applies. A joomiz validate or joomiz register error that says an id "must be kebab-case" is always this same rule.

Two scopes are worth knowing up front:

  • An entry's id under artifacts or tooling only has to be unique within the whole application. Both are top-level keys, declared once for the whole file, so nothing scopes their ids per environment.
  • An entry's id under targets, deployments, managed-resources, or consumed-resources only has to be unique within its own environment. test and prod are different environments, so each can declare its own managed-resources entry called billing-service-db — and the two examples in this guide do exactly that.
