Joomiz is a platform-engineering Golden Path for Spring Boot services. You describe your application, its tooling, and its infrastructure in one file, joomiz.yaml, and the Joomiz CLI and control plane turn that description into running infrastructure.

This guide documents that file: its structure, its fields, and the syntax you use to reference one part of it from another.

Who this guide is for

You're a developer who owns a Spring Boot service and wants to write or edit its joomiz.yaml. You don't need to know how the Joomiz control plane works internally — you need to know what to write in the file and why.

Before you start

Two real, working files back every example in this guide:

  • platform/shared/examples/order-service/joomiz.yaml — a service deployed to Kubernetes.
  • platform/shared/examples/billing-service/joomiz.yaml — a service deployed to Cloud Foundry, with a managed secret store.

Open one of them alongside this guide. Every snippet here is a real excerpt from one of the two, not an invented one.

Read the guide in this order

  1. Control plane, catalog, and Golden Path — three terms this guide uses often, defined once before you need them.
  2. Anatomy of a joomiz.yaml file — the file's overall shape, and the one identifier rule every id in the file follows.
  3. The application block — your service's identity and its owner, plus the artifacts and tooling lists written beside that block.
  4. The environments block — where your service runs, what it deploys, and what infrastructure it needs.
  5. Reference expressions — the ${{ ... }} syntax you use to point one part of the file at another, such as a deployment's environment variable at a managed resource's output.

How you use this file

A joomiz.yaml moves through the Joomiz command-line tool in stages. Each stage is a separate command:

  1. joomiz init — scaffolds a new joomiz.yaml with your application's identity and owner. It writes a local file only; it never contacts the control plane.
  2. joomiz register -f joomiz.yaml — submits the file to the control plane for the first time. Registration stores your application's identity, its owner, and the top-level artifacts and tooling lists. It does not read the environments block or application.metadata at all — those sections matter starting at the next step.
  3. joomiz validate -f joomiz.yaml — checks the whole file, including environments, against the control plane's rules, and reports every problem it finds. It changes nothing.
  4. joomiz plan --environment <name> -f joomiz.yaml — shows what applying this file would change in one environment. It changes nothing.
  5. joomiz apply -f joomiz.yaml — executes a plan you've already reviewed.

Because registration ignores environments and application.metadata, a file can pass register while still having problems in those sections. Run validate before you rely on the whole file being correct.

Which tool and resource types can you use?

It depends on what your control plane has configured. Each tool, artifact, target, deployment, managed-resource, and consumed-resource has a type field, and every type value you write must match an entry your control plane's catalog has registered. Your platform team controls that catalog. They add or change an entry by releasing a new version of the control plane — so the exact list is specific to your installation, not something this guide can print once and keep accurate.

Wherever this guide names a type value, such as postgres or kubernetes-deployment, it's quoting a real value from the examples. It is not documenting a closed list.

To see the exact catalog your control plane currently has, fetch GET /schema from it, or open the file in an editor running the Joomiz Language Server, which fetches the same endpoint for completion and validation.

The rest of joomiz.yaml isn't specific to your installation this way. The key names, the nesting, and the reference syntax described in this guide are the same on every Joomiz control plane.
