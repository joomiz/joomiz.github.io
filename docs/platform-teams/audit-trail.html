Goal

For platform teams. In this task you read who did what in the control plane. You set how long events are kept. You also remove a person from the trail when someone asks you to. The audit trail is the list of the actions that people and the control plane made.

Before you start

  • You have the CLI, and you are signed in. Sign in and get access shows how.
  • To read every event, to filter by user and to erase a person, you need the role operator. A person with the role owner:<team> reads only the events of the applications of that team.
  • For an erasure you need a second operator. An operator cannot erase their own ID.

Steps

Know what is recorded

The control plane records these actions. Each action has its own name:

Action When it is recorded
provisioner.registered A provisioner is registered.
provisioner.updated A registration is changed.
provisioner.deregistered A registration is removed.
application.registered An application is registered.
apply.requested Someone asks for an apply. The event is recorded when the apply starts, and also when the control plane refuses it because another apply holds the lock.
run.abandoned An operator or the control plane releases a run.
audit.subject_erased An operator erases a user from the trail.

A plan, a validate and every read are not recorded.

Each event holds these facts:

Field What it holds
occurredAt The time of the action.
action The name of the action.
outcome performed, or refused with a reason such as apply_in_progress.
actorKind The account type: person, service or system.
actorSubject The ID of the user, as the identity provider gives it. It is never a name. A system event has none.
authority The role that the user acted as, for example operator or owner:finance-team. It is system for an event of the control plane itself.
targetType and targetId What the action was about: a provisioner, a run, an application or an erasure.
applicationId, environment, runId The application, the environment and the run, when the action has them.
traceId The trace of the call, when the control plane sends traces.

An event is written in the same step as its action. If the control plane cannot write the event, it does not do the action, and it answers 503.

Know the events of the control plane

The control plane writes some events itself. For example, it releases a run that wrote no event for a long time. Such an event has the account type system, the role system and no user ID. The CLI prints a dash in the column of the user ID. The JSON answer has no actorSubject:

Read the trail in the dashboard

The page Audit of the Platform dashboard shows the same events, newest first. The columns are Time, Action, Outcome, Authority, Actor, Subject and Target. The filters are the action, the outcome, the application ID, the run ID, and the times From and To. The button Load more events shows the next page. The filters stay in the address of the page, so you can share a search. Use the Platform dashboard describes the other pages.

The column Subject shows the user ID as plain text, (erased) after an erasure, and a dash for an event of the control plane itself. A person with the role owner:<team> also sees a dash for the event of an operator.

See what an owner sees

A person with the role owner:<team> reads the events of the applications of that team. The ID of an operator is hidden from that person. The CLI shows (hidden) in the column:

An owner cannot filter by user ID. The control plane answers 403 for --actor.

Read the trail with HTTP

The call is GET /audit-events. The query names are in snake_case: application_id, run_id, action, outcome, actor_subject, from, to, cursor and page_size. The page size is from 1 to 100, and the default is 50. When more events exist, the answer has a nextCursor. Send it as cursor for the next page. The control plane sends each answer on one line. The examples here have line breaks, so that you can read them. The field actorSubject is missing for an event of the control plane itself and for the event of an operator that an owner reads. For an erased event it is missing too, and the field actorErased is true. Control plane API reference shows the call with a token that is not on the command line.

curl -s -w '\nHTTP %{http_code}\n' --variable '%JOOMIZ_TOKEN' --expand-header 'Authorization: Bearer {{JOOMIZ_TOKEN}}' "$JOOMIZ_SERVER_URL/audit-events?from=2026-10-28T19:18:00Z&action=run.abandoned&page_size=1"

{"detail":"audit query is invalid: outcome must be one of performed, refused","status":400,"title":"Invalid audit query"}
HTTP 400

Set how long events are kept

The control plane deletes events that are older than joomiz.audit.retention. The value is from 90 to 3650 days. The default is 400 days. The environment variable is JOOMIZ_AUDIT_RETENTION, for example 400d. A value outside the range stops the start of the control plane, and the error names the setting. A job runs every hour and deletes the old events in small steps. Settings reference lists the settings of the job.

Erase a person from the trail

A person can ask to be removed from the records. You erase the user ID of that person. The events stay, with their action, their target, their role and their time. Only the ID is removed, and the events show (erased) in its place.

  1. Get the user ID of the person from your identity provider. Write the request and the date in your own records. Joomiz does not keep the erased ID.
  2. Find the events of that ID. This shows what the erasure will change:
joomiz audit --from 2026-10-28T19:18:00Z --actor 5d0f2c6e-9a41-4e1b-8c37-2b7f6a1d9e03

TIME                      ACTION               OUTCOME    KIND    SUBJECT                               AUTHORITY  TARGET
2026-10-28T19:20:16.016Z  run.abandoned        performed  person  5d0f2c6e-9a41-4e1b-8c37-2b7f6a1d9e03  operator   run:74c4e9a7-beb9-4557-bcdb-c5ccc2d730f4
2026-10-28T19:19:00.680Z  provisioner.updated  performed  person  5d0f2c6e-9a41-4e1b-8c37-2b7f6a1d9e03  operator   provisioner:f690396e-d272-454e-886a-2f3e8e8cb458
  1. Ask another operator to send the erasure. The body has exactly one field, subject:
curl -s -w '\nHTTP %{http_code}\n' --variable '%JOOMIZ_TOKEN' --expand-header 'Authorization: Bearer {{JOOMIZ_TOKEN}}' -X POST -H 'Content-Type: application/json' -d '{"subject": "5d0f2c6e-9a41-4e1b-8c37-2b7f6a1d9e03"}' "$JOOMIZ_SERVER_URL/audit-erasures"

{
  "id": "c0799010-9fba-4c48-8415-6637281cb15b",
  "erasedEvents": 2
}
HTTP 201

After a restore from a backup

A restore from a backup brings back the events as they were on the day of the backup. The erased IDs return with them. Send the erasure requests again that you received after the date of the backup. Use your records of the requests, because Joomiz does not keep the erased ID.

Check

  • joomiz audit as an operator prints events, and as an owner it prints fewer and hides the IDs of operators.
  • After an erasure, joomiz audit --actor <id> prints no audit events found.
  • The setting joomiz.audit.retention is in your configuration, and it is the value that you decided.

Troubleshooting

Symptom Cause Fix
403 and Operator role required for --actor or for an erasure You have only the role owner:<team>. Sign in as an operator.
403 and an operator cannot erase their own subject The ID in the body is your own. Ask another operator to send the erasure.
400 and Invalid audit erasure The body is not exactly {"subject": "..."}, or the ID is empty or too long. Send one field subject with 1 to 255 printable characters.
400 and Invalid audit query A filter has a bad value. Read the text. It names the rule.
503 and audit-unavailable The control plane could not write the audit event. Try again later. The action was not done.
--limit must be a number from 1 to 1000 The number is outside the range. Use a smaller number.
The control plane does not start and names joomiz.audit.retention The value is below 90 days or above 3650 days. Set a value in the range.
