The application block describes your service's identity: who owns it and where its code lives. This page covers that block, plus the two lists written beside it and declared once for the whole file: artifacts and tooling.

Each snippet below shows one section on its own. application is indented as its own block; artifacts and tooling start at the left margin, because they are top-level keys — siblings of application, not fields of it. See Anatomy of a joomiz.yaml file for how the pieces sit together.

Scalar fields

application:
  id: 7c1a1e2a-4b3d-4f0a-9c2e-5f6a7b8c9d0e
  name: order-service
  description: Handles order creation, payment status, and fulfillment events.
  repository: https://github.com/joomiz-demo/order-service
  golden-path: java-web-application
Field Required Format Notes
id Yes A UUID, written in its standard lowercase form You choose this value — the control plane never generates it. Write it once, when you create the file, and don't change it afterward. It's how the control plane recognizes this application on every later register, validate, plan, and apply.
name Yes Kebab-case, at most 255 characters The human-facing name. It doesn't have to be unique — id is the only thing that identifies an application.
description No Free text, at most 4096 characters A blank value is treated the same as leaving the field out.
repository Yes An https:// URL, at most 2048 characters The control plane checks this for valid syntax only. It never fetches the URL, so this field is safe to point at a private repository.
golden-path Yes One of a fixed set of values The Golden Path this service is built on. As of this writing, the two available values are java-web-application and kotlin-web-application. The control plane rejects any other value. If neither of these fits your service, check with your platform team for the current list.

Why id is your application's only identity

id is the only thing that identifies your application. Two applications can share the same name, but they can never share the same id. Generate it once — joomiz init does this for you if you don't pass --id — and keep it in the file for the application's whole lifetime.

The owner block

  owner:
    id: commerce-team
    name: Commerce Team
Field Required Format Notes
owner.id Yes Non-blank, at most 255 characters, no control characters A free-form team slug, such as commerce-team. It doesn't have to be kebab-case.
owner.name Yes Non-blank, at most 255 characters A human-readable team name, such as Commerce Team.

An owner is shared across applications. If two applications register with the same owner.id but a different owner.name, the most recently registered name wins. Registering an application always updates its owner's stored name to match the file.

The metadata block

  metadata:
    configuration-item: CI-00123

metadata is a free-form map. The control plane doesn't validate its shape or its keys — write whatever annotations your organization needs, such as a change-management ticket reference.

Even though nothing validates it, metadata isn't purely decorative. A reference expression elsewhere in the file can read one of its keys, such as ${{application.metadata.configuration-item}}. Note that metadata is one of the sections joomiz register doesn't read — see How you use this file.

The tooling list

tooling:
  - id: renovate
    type: renovate
    enabled: true
    spec:
      schedule: before 6am on monday

  - id: checkmarx
    type: checkmarx
    enabled: true
    spec:
      scan-on: pull-request
      severity-threshold: high

Each entry configures one piece of tooling for this application — a dependency-update bot, a security scanner, and so on.

Field Required Format Notes
id Yes Kebab-case, unique within the application Your own name for this entry.
type Yes Must match a tool type the control plane's catalog has registered renovate and checkmarx, shown above, are two real registered types — not an exhaustive list. See Which tool and resource types can you use?.
enabled No true or false Defaults to true when you leave it out.
spec Yes (shape depends on type) A map whose required fields are defined by the catalog entry for type schedule and scan-on/severity-threshold, above, are spec fields specific to renovate and checkmarx. A different tool type requires different spec fields.

Unlike artifacts below, an application can't declare two tooling entries with the same type. For tooling, both id and type must be unique within the application.

A tooling entry's spec, serialized as JSON, is capped at 16 KB, and an application may declare at most 50 tooling entries.

The artifacts list

artifacts:
  - id: order-service-image
    type: container-image
    spec:
      dockerfile: Dockerfile
      registry: ghcr.io/joomiz-demo/order-service

Each entry describes one thing your build produces — a container image, a JAR, and so on. A deployments entry in the environments block (see The environments block) refers back to one of these by its id.

artifacts:
  - id: billing-service-jar
    type: jar
    spec:
      path: target/billing-service.jar
Field Required Format Notes
id Yes Kebab-case, unique within the application This is the id a deployments entry's artifact field names.
type Yes Must match an artifact type the control plane's catalog has registered container-image and jar, shown above, are two real registered types — not an exhaustive list.
spec Yes (shape depends on type) A map whose required fields are defined by the catalog entry for type dockerfile/registry and path, above, are spec fields specific to container-image and jar.

Unlike tooling, artifacts has no enabled field. Its type also doesn't have to be unique. A service that builds two container images, or several JARs from a multi-module build, declares one artifacts entry per build output. Each entry gets its own id.

An artifacts entry's spec, serialized as JSON, is capped at 16 KB, and an application may declare at most 50 artifacts entries.
