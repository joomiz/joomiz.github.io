Security and compliance

Keep secrets out of repositories

Put a reference in joomiz.yaml instead of a password. The provisioner stores the secret in a vault and reports its address. The control plane keeps only that address.

Email us Read the docs

Without Joomiz

Passwords end up in repositories, tickets, chat and pipeline settings. Copies multiply, and nobody can say who has seen one. After a leak, teams search every project to find and rotate them.

With Joomiz

  1. Write a reference

    In the file, name the output of the resource that owns the secret. The text ${{ ... }} is a reference. It is not a value.

  2. Preview without a secret

    The plan shows (known after apply) for the value. The plan, and the apply after it, never print the password.

  3. Pass only an address

    After apply, the application receives the address of the secret in the vault. It reads the secret from there. The file and the control plane never hold the secret.

  4. Refuse a raw value

    A sensitive output must be an absolute address. If a provisioner returns a value instead, the plan fails and says so.

What you get

  • A joomiz.yaml that is safe to review, share and show to an assistant.
  • Plan and apply output that shows addresses, never passwords.
  • Secrets that stay in the vault of your platform.

The rules that still hold

  • A sensitive output must be an absolute address. A raw value fails the plan.
  • A reference to a value the type does not declare fails joomiz validate.
  • Your platform team decides which vault holds secrets and how an application reads them.
