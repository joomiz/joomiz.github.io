Turn your automation into a provisioner within your rules

Put a script, a pipeline or a cloud API behind the provisioner contract. The catalog entry of the type lists every setting a team may write. Feature teams ask only for what you allow.

Email us Read the docs

Without Joomiz

Each team asks for infrastructure in its own way. Scripts and pipelines have no shared contract and no shared check of what a request may contain. The platform team reviews requests manually and cannot see what was asked.

With Joomiz

  1. Map a type to a pipeline

    The Azure DevOps pipeline provisioner starts a pipeline you already own, for each category and type you map. The pipeline reports its result in a callback.

  2. Or answer the contract yourself

    Any service that answers POST /plan, POST /apply and POST /inspect can be a provisioner. It receives one change set for each category and type.

  3. Register it against a closed schema

    Register the provisioner for its category and type. The catalog entry of that type lists the allowed settings and refuses all others.

  4. See a request refused

    A setting outside the schema fails joomiz validate with a message that names the setting. Valid requests then go through plan and apply.

What you get

  • Existing automation that feature teams use through one file and the Joomiz CLI.
  • Requests checked against your schema before your automation runs.
  • A plan that previews every change before apply.

The rules that still hold

  • Each category and type has one provisioner. A second claim is refused.
  • The control plane checks outputs against the catalog entry. A value that does not fit fails the change.
  • A password is never an output value. The provisioner reports the https address of the secret.
