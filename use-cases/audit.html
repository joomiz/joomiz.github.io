Security and compliance

Show who changed what

Joomiz records every apply, registration, provisioner change and run release with the person's ID, their role and the target. Read the trail with joomiz audit or on the dashboard Audit page.

Email us Read the docs

Without Joomiz

After an incident, someone must find who applied a change and when. The answers sit in chat, CI logs and memory. Each system names people in its own way, so the trail has gaps.

With Joomiz

  1. Read the trail

    joomiz audit prints the newest events first. Filter by action, application, run, outcome or time. An operator can also filter by user ID.

  2. Follow one run

    Filter by run to see the events around it. A refused apply is recorded too, with its reason.

  3. Let teams see their own events

    A person with the role owner:<team> reads only the events of the team's applications. The ID of an operator shows as (hidden).

  4. Set retention and erase on request

    Events are kept for joomiz.audit.retention, from 90 to 3650 days. A second operator can erase a person's ID. The events stay and show (erased).

What you get

  • One trail that names the person, the role, the action and the target.
  • An answer to "who applied this?" in one command.
  • A trail that respects an erasure request and a retention limit.

The rules that still hold

  • An event is written with its action. If the write fails, the action is not done.
  • An owner reads only its own applications and never sees an operator's ID.
  • An operator cannot erase their own ID. The erasure is recorded too.
